# 2.2 - Types

## Definition

Types in Minimal defines what kind of data we are dealing with;
they say if we are dealing with numbers, text or something else.

Minimal is a _statically-typed_ programming language, which means the types _must_ be known at compile-time
(before the program runs; when the compiler is compiling your code), and not at runtime, like JavaScript.

Recall the code we wrote in the last document:

```rust
let x = 10;
```

Generally in statically-typed languages, like Java, we see the variable types in the declaration.
But we are not writing any types here. How does the compiler know the type?

What is happening here is the _type inference_, which is a compiler mechanism that dictates the type
of the variable based on the value you give to it.

Here, we gave `x` the value `10`, an integer literal, which has a known type to the compiler as `int`. <br />
So, the compiler takes the type of the expression and assigns it to the variable.

---

Minimal divides its types into two groups: _concrete_ and _abstract_.

_Concrete_ types are those that are manipulated directly by the programmer and can be assigned to variables.
Every valid value in Minimal fits into one of these.

_Abstract_ types only exist in expressions and should never go to a variable. They must coerce to another type before being assigned to one.
These types exist because they allow the language to provide its powerful features, such as _type inference_.

There is an abstract type called `never` that doesn't coerce to any type, so a variable with this type cannot exist, and its declaration will be omitted from the final bytecode.

All _concrete_ types are representable via syntax (i.e. can be told via a type annotation, such as `int`), but not all _abstract_ types can.

## List of types

This is the list of all types supported by Minimal:

- Concrete types:

Name|Description|Size|Range
---|---|---|---
`int`|Represents an integer number.|32 bits (4 bytes).|`-2^31` to `2^31 - 1`
`float`|Represents a floating-point (decimal) number.|64 bits (8 bytes).|`-1.7e+308` to `+1.7e+308`.
`str`|Represents a sequence of characters.|Variable.|Variable.
`char`|Represents a single character.|8 bits (1 byte).|`0` to `255`.
`bool`|Represents either `true` or `false`.|8 bits (1 byte).|`true` or `false`.
`void`|Represents no value.|No size; only type tag.|`void`.
`T?` (optional)|Represents a type that may not have a value.|Same as `T`.|Same as `T`, plus `nil`.
`fn` (function)|Represents a function or a closure with the specified argument and return types.|Enough to fit the name, the chunk of code (see [chunk] in the technical book) and the number of arguments (arity), or just the size of a pointer plus the arity if it points to a native function; actual size depends on the implementation and the platform.|All valid functions and closures.
`range<T>`|Represents a range or an interval of numbers or characters.|Size of `T` * `3`, plus the size of `bool`.|Any combination of the supported types (`int`, `float` and `char`), both inclusive and not.
`never`|Represents an expression that doesn't behave normally and therefore has no valid value. Most statements that change control flow assign this type to the block they are in.|No runtime representation.|No valid value.|

- Abstract types:

Name|Description|Size|Range|Types it can coerce to|Representable via syntax
---|---|---|---|---|---
`untyped nil`|Represents no value, in a context of optionals.|No size; only type tag.|`nil`.|Any optional type (`T?`).|No.
`_` (unknown)|Represents a type that is yet to be inferred (i.e. the compiler doesn't know it yet, but it needs to know before assigning a value with this type to a variable; otherwise it will throw a compiler error).|No runtime representation.|Any valid value in Minimal|Any type.|Yes.

### Extra information

- Why `any` isn't there?
    `any` is a type in many statically-typed programming languages, such as Kotlin, that aims to represent any possible value in the language,
    mimicking the behavior of dynamically-typed programming languages, such as Python.
    By allowing so, the language's type checker would need to be disabled in order to allow such a thing.
    By disabling the type checker, a _runtime_ checker would be needed to continue providing type safety,
    which a conforming implementation for Minimal doesn't need to have.
    because the compiler should handle all the type checking.
    We could restrict the `any` type to only be written to, but not read from, unless a type conversion is made. But for now, such mechanism
    haven't showed necessary. But maybe for a future release, some kind of `any` may be included.

- Why `never` is concrete?
    `never` is the strangest of the concrete types, strongly resembling an abstract one.
    Like explained above, it represents a value that will _never_ exist. It is considered concrete because unlike the other abstract types,
    it _can_ be assigned to a variable. But a variable with the type `never` won't behave naturally,
    like the others: because `never` has no valid value, there is no point of a variable with this type to exist,
    so it can be safely removed from the code, and a warning will pop up.

## Type annotations

Although type inference is handy, we can't use it always, though.
To still allow your program to compile, Minimal gives the programmer the ability to annotate the types themselves. Here is an example:

```rust
let x: int = 10;
```

This is the same variable as before, but now we annotated its type explicitly. <br />
In most cases, we don't need to do this, because the compiler's type inference algorithm will fill it for us.

### Cautions

But there are some things that we need to care about.

#### 1. Wrong type annotation

If we annotate a type that is not compatible to the value we gave to it, the compiler will throw an error.

Take this code:

```rust
let x: str = 10;
```

We are annotating the variable with the type `str` and giving an integer number to it. <br />
This doesn't make sense. How can a string type hold an integer?

#### 2. Type inference can't infer everything

Type inference is very handy, making us not having to write the types of our variables and of some expressions. But it doesn't always work.

Type inference can fail, and thus require the programmer to write the type explicitly.

Take this case:

```rust
let x = nil;
```

`nil` is a keyword used in optional types (see [optionals]) to denote the absence of a value. <br />
But it needs to be assigned an optional type (like `int?`, which is an optional integer: it can have all
values an `int` can have, plus `nil`).


If we give it only the value `nil`,
how can the inference algorithm guess that we wanted to type the variable as `str?`, for example?

It can't, this is because it requests the programmer to write its type explicitly to remove the ambiguity.

> Advanced Note:
> The list above tells us that there is an `untyped nil` type, that is the default type of the `nil` expression;
> it's an abstract type, so it cannot go into variables, so it must coerce into a concrete type first, which is an optional type (`T?`).

We can fix the error in two ways:

##### Annotating the variable

The most straightforward way to fix the error is by annotating the variable:

```rust
let x: str? = nil;
```

> Note that the algorithm will still check if the type is compatible with the value. The compiler will still throw an error if 
you try to annotate the variable with a non-optional type, like `str`.

`nil` itself has a generic type that coerces automatically to any optional type, and by annotating the variable,
the generic type of `nil` turns into the specific optional type of the variable.

Now the error goes away.

##### Annotating the value

`nil` has a special syntax used to disambiguate the type at the _expression level_, that means, the value itself,
and not the variable, will be annotated with the type.

This is how you do it:
```rust
let x = nil<str?>;
```

This way, we tell the compiler that this `nil` is the absence of value of an optional `str` type (`str?`), and not of any type. Now the inference algorithm can correctly infer the type of the variable.

You can also use type casts (see [casting]):

```rust
let x = nil as str?;
```

Both ways work.

There are more cases where the inference algorithm can't do the job alone and we need to help it,
but to fix the error we just need to annotate the types ourselves. But in the majority of cases we don't need to do that.
